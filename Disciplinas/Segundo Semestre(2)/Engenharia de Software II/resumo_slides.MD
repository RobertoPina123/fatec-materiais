# Slide 1 - Introdução

## Engenharia de Requisitos

- Campo da engenharia de software que se concentra na identificação, documetação, análise, validação e gerenciamento
dos requisitos de um sistema de software. 
- Envolve o processo de entender, capturar e definir de maneira sistemática as necessidades dos Stakeholders. ( Clientes, usuários finais,
equipes de desenvolvimento,etc.) 

## Quem são os Stakeholders

- Individuos, grupos ou entendidades que tem interesse ou envolvimento no desenvolvimento e
no resultado de um projeto ou sistema.
- Ajudam diretamente na definição dos requisitos do projeto

### Clientes: 

São aqueles que contratama construção do software e tem interesse direto nos resultados finais. 

### Usuários Finais: 

Pessoas que usarão o software no dia a dia. 

### Equipe de Desenvolvimento: 

Isso inclui desenvolvedores, designer, analistas, testadores e outras pessoas 
envolvidas na criação do software.

### Gerentes de Projeto: 

Responsáveis por coordenar e supervisionar todas as atividades do projeto. Incluindo a comunicação com os Stakeholders, o cumprimento dos prazos, 
e o gerenciamento de recursos. 

### Analistas de Negócios:

Responsáveis por compreender e articular as necessidades dos clientes e usuários, traduzindo em requisitos claros e compreensíveis para a equipe de desenvolvimento. 

### Equipe de Testes: 

Testar o software para saber se ele atende os requisitos estabelecidos, identificando problemas e garantindo a qualidade do produto final. 

### Equipe de Suporte: 

Responsável por lidar com problemas, fornecer suporte técnico e garantir que o software funcione conforme esperado. 

### Reguladores e Órgãos Governamentais: 

Regulam através das leis, o que os softwares podem fazer ou não. 

# Introdução 

- Definição de Engenharia de requisitos: 

Abordagem sistemática e disciplinada para a especificação e gerenciamento de requisitos com os seguintes objetivos: 

> CONHECER OS REQUISITOS RELEVANTES:
> estabelecer um consenso entre stakeholders a respeito de tais requisitos, documentar os requisitos, 
> de acordo com determinados padrões e gerenciar os requisitos de forma sistemática. 

> COMPREENDER E DOCUMENTAR: 
> As expectativas e necessidades dos stakeholder, especificar e gerenciar os requisitos para minimizar o risco de entregar um sistema que não atenda 
> as suas expectativas e necessidades. 

- Importância da engenharia de Requisitos: 

       - Impacto no desenvolvimento de sucessos e focados no cliente. 
       - Tornou-se prática comum destinar recursos a engenharia de requisitos
       - Envolve uma seria de atividades complexas
       - 60% de todos os erros em projetos de desenvolvimento de softwware tem origem durante a fase Engenharia de Requisitos. 
       - Esses erros costumam ser descobertos em fases mais avanaçados do projeto, ou depois de implementado. 
       - A falta de requisitos muitas vezes não é dectatada durante a fase de projeto e execução. 
       - Desenvolvedores confiam nos requisítos trazidos pelos Engenheiros de Requisítos. 
       - Quanto mais avançado o projeto, mas caro a correção de um erro nos requisítos.
        

- Meta da Engenharia de Requisítos: 

       - Elicitar os requisítos dos stakeholders
       - Documentar de forma correta
       - Validar e Verificar os requisitos
       -  Gerenciar esses requisitos ao longo de todo ciclo de vida do sistema
        
- Sete Tarefas Distintas da Engenharia de Requisitos:

       - Concepção
       - Levantamento
       - Elaboração
       - Negociação
       - Especificação
       - Validação
       - Gestão
# Passo 1 - Concepção 

## Como um projeto de Software é iniciado?

- Identificação das Necessidades do Negócio

- Descoberta de um novo serviço ou mercado. 

## Tarefas da Concepção

- Entendimento básico do problema

- Definição das pessoas que querem uma solução

- Natureza da Solução Desejada

- Eficácia da comunicação entre as pessoas e os desenvolvedores

# Passo 2 - Levantamento 

## Perguntas úteis

- Quais os objetivos do software?

- O que deve ser alcançado? 

- Como o software atenderá as necessidades da empresa

- Como o software será utilizado no dia-a-dia?

## Problemas Comuns

- Limites especificados de forma precária

- Detalhes Técnicos desnecessários elicitados

- Problemas de Entendimento - Clientes e usuários não estão certos das suas necessidades

- Entendimento inadequado das capacidades e das limitações dos ambientes computacionais 

- Requisitos mudam o tempo todo

# Passo 3 - Elaboração

- Expansão das informações obtidas durante as fases de concepção e levantamento 

- Criação e Refinamento de cenários de usuários que irão interagir com software. 

- Desenvolvimento de um * Modelo de requisitos * refinado

# Passo 4 - Negociação 

- Clientes podem solicitar mais do que pode ser alcançado, considerando os recursos do negócio. 

- Diferentes clientes e usuários propõem requisitos diferentes e conflitantes. 

- Necessidades de conciliar conflitos com negociações

# Passo 5 - Especificação

- Software Requirements Specication -  SRS ( Especificação de Requisitos de Software) 

- Documento Criado quando uma descrição detalhada de todos os aspectos de software é especificada. 

# Passo 6 - Validação 

- Avaliar a qualidade dos requisitos levantados

- Examinar a especificação para garantir que todos os requisitos são claros, consistente, sem omissões ou erros. 

# Passo 7 - Gestão

- Conjunto de atividades que ajuda a equipe de projeto a identificar, controlar e acompanhar as necessidades e suas mudanças. 

# Teoria da Comunicação - Linguagem como Meio de Comunicação de Requisitos

- Requisitos precisam ser comunicados

- Na maioria dos casos utiliza-se um meio de comunicação regrado e acessível ao parceiro de comunicação (linguagem natural) 

- É necessário um código comum entre ambas as partes para que a comunicação seja eficiente. 

- Quanto maior a semelhança entre: Suas origens culturais, educacionais, áreas de especialização e suas rotinas diárias de trabalho, 
melhor será a comunicação entre eles. Essas condições ideias geralmente não existem. 

## Tipos de meio de Comunicação 

- COMUNICAÇÃO VERBAL: Sucesso da comunicação depende fortemente da redundância ( gestos, linguagem, entonação) 

- COMUNICAÇÃO ESCRITA: Mínimo de redundância e feedback. 

## Acomodação Linguística 

- Além dos problemas decorrentes de diferentes vocabulários de domínio e diferentes meios de comunicação, pode-se muitas vezes observar 
que as informações não são transmitidas de forma correta. 

- Esses problemas podem ser atribuídos a transformações da percepção natural. 

# Tipos de Requisitos 

## Funcionais 

- Definem a funcionalidade oferecida pela sistema a ser desenvolvido. 

- São requisitos relacionados ao resultado de algum comportamento a ser fornecido por uma função do sistema. 

- Exemplo: Tipos de transação suportadas, meios de autenticação. 

## Requisitos Não-Funcionais 

- Definem qualidades desejados do sistema a ser desenvolvido e muitas vezes influenciam a arquitetura do sistema 
mais do que os requisitos funcionais. 

- Definem o desempenho, a disponibilidade, a confiabilidade , a escabilidade ou portabilidade de um sistema.

- Exemplo: Facilidade de uso, tempo de respostas,  implementação para um certo Sistema operacional.

# Passo 1 - Técnicas de Pesquisa 


- Técnicas de pesquisa tem por objetivo elicitar as mais precisas e imparciais DECLARAÇÕES possíveis dos stakeholders a respeito de seus requisitos.

- As técnicas de pesquisa parte da ideia de que o entrevistado é capaz de expressar claramente seus conhecimentos e está comprometido a investir tempo e esforço 
para elicitação. 

## Entrevistas 

- TÉCNICA DE PESQUISA - ENTREVISTA: Conversas diretas entre um facilitador e um ou mais stakeholders. Podem ser estruturas, semi-estruturada, ou não estruturadas. 
       
      * Entrevistas Estruturadas: Envolvem uma série de perguntas pré-definidas que são feitas a todos os entrevistados. Respostas consistentes, comparações entre participantes.
      * Entrevista Semi-Estruturada: O entrevistador tem um conjunto de perguntas pré-defindas, mas também tem flexibilidade para explorar tópicos que surgem durante a conversa. 
      * Entrevistas Não-Estruturadas: São mais informais e não possuem roteiro fixo. 
      * Entrevistas podem ser usados em toda a fase de desenvolvimento. 

- Desafios da Pesquisa: 

       - Vies do entrevistador - O entrevistador pode sem querer influenciar as respostas do entrevistado. 
       - Vies dos participantes - Os participantes podem inputar suas própias opniões pessoais e perpectivas subjetivas. 
       - Tempo - Entrevistas podem ficar longas e cansativas. 
       - Por vezes as informações podem ser confidenciais
    
- Análises:

    - Revisar as Notas ou transcrições das entrevistas. 
    - Identificar padrões, insights e informações relevantes
    - Agrupar informações semelhantes 
    - Documentar conclusões e informações obtidas nas entrevistas

- Tipos de Perguntas: 

    - Perguntas abertas: Perguntas amplas que incentivam os entrevistados a fornecer respostas detalhas e expansivas
    - Perguntas Fechadas: Respostas Específicas, sim ou não, 
    - Perguntas de Múltipla-escolha: Essas perguntas fornecem opções pré-definidas para serem escolhidas. Comum para perguntas quantitativas.

## Questionário 

- Elaborados com questões abertas e fechadas

- Para muitos participantes, questionários online podem ser úteis

- Elicitam um grande numero de questões rapidamente

- Somente servem para os requisitos que o analista já conhece

- Questionários precisam ser bem preparados e elaborados

- Não fornecem retroalimentação 

- Variáveis do Questionário: 
    
    - Qualitativa(Categórica) - Nominal/Ordinal 
    
    - Quantitativa(Numérica) - Discreta/ Contínua

### Qualitativas Nominais 

Usado para representar características que não possuem uma ordem natural ou hierarquia. Exemplo: Cor dos olhos, País de origem, Estado Civil, tipo sanguíneo. 

### Qualitativas Ordinais 

Representa características que podem ser ordenadas ou classificadas em uma ordem específica. Elas tem uma hierarquia natural, mas não obedecem uma ordem numérica.
Exemplo: Ensino Fundamental Completo, ensino médio incompleto, Ensino médio completo, Graduação, pós graduação. 
Exemplo: Classe Social: Baixa, media, alta. 
Exemplo: Nível de Concordância: Discordo Totalmente, Discordo parcialmente, neutro, concordo parcialmente, concordo totalmente ( Escala de Likert). 

> Exemplo da Escala de Likert: \
> " Estou satisfeito com meu trabalho"\
> 1 - Discordo totalmente \
> 2 - Discordo \
> 3 - Neutro \
> 4 - Concordo \
> 5 - Concordo totalmente 

### Quantitativas Discretas 

Representa contagens ou medidas específicas que só podem assumir valores inteiros e isolados. São diferentes das variáveis quantitativas contínuas, que podem assumir
valores em uma escala contínua e incluir decimais. 

- Características: 
    - Valores Inteiros
    - Conjunto Contável 
    - Sem espaços vazios ou não observados na variável. 
    
Exemplos de quantitativas discretas: 
    - Número de Filhos em uma família 
    - Número de acidentes de trânsito em uma cidade durante um mês 
    - Número de estudantes em uma sala de aula

### Quantitativas Contínuas 

Representa medidas que podem assumir qualquer valor em um intervalo contínuo. Ao contrário das discretas que assumem valores inteiros, as contínuas
assumem valores em uma escala infinitamente divisível. 

Exemplo: Altura de uma pessoa, pode variar entre um valor de 150 cm a 180 cm.
Exemplo: Tempo de reação: Podem variar em uma escala contínua entre 0,2 a 1,5. 
Exemplo: Peso de um objeto: Pode variar em qualquer valor dentro de um intervalo contínuo, como de 2kg a 5kg.

# Passo 2 - Técnicas de Criatividade

## Brainstorm: Usada para estimular a criatividade e a coleta de informações. Tem por objetivo criar um ambiente 
aberto colaborativo onde os participantes possam gerar livremente uma variedade de ideias. 

- Preparação:Reunir um grupo de participantes(5 a 10) que tenham conhecimento relevante sobre o problema ou requisito. 

- Definição do Problema: Todos precisam ter uma definição comum do que será discutido. 

- Estabelecimento de Regras: Definir algumas regras básicas, como não criticar as ideias, encorajar a quantidade e não a qualidade, incentivar o aproveitamento
das ideias uns dos outros. 

- Geração de ideias: Os participantes começam a gerar ideias de forma livre e sem restrição, todas as ideias são válidas, e o ambiente deve ser sem julgamentos. 

- Registro: Todas as ideias são registradas. Sem exceção. 

- Discussão e expansão: Após a fase de geração, as ideias são revisadas e discutidas. 

- Vantagens: Muitas ideias em um curto período de tempo, ideias são expandidas colaborativamente, novas soluções podem surgir de forma inesperada. 

- Desvantagem: Menos eficaz se o grupo for confuso, ou houver membros muito dominantes

### Técnicas alternativas - BrainWriting

Uma abordagem mais silenciosa, útil em cenários em que os participantes não se sentem a vontade em público.


### Técnicas Alternativas - BrainStorming Paradox 

Brainstorm ao contrário. Diz respeito a tudo que não pode ser feito e não pode acontecer. 

## Six Thinking Hats 

Ajuda a contrariar o pensamento argumentativo(onde cada um defende seu ponto de vista), mas incentiva o
pensamento paralelo, onde todos devem em cada momento olhar sobre uma perspectiva específica. 

- Todos usam juntos a mesma cor 
- Falam somente se tem algo sobre aquilo naquele momento
<pre>
``` 
* [Foco Analítico: Baseado em Dados e Análise]
  └── Chapéu Branco (Factos, Informações, Neutro)
  └── Chapéu Preto (Pontos Fracos, Ameaças, Negativo)
  └── Chapéu Amarelo (Pontos Fortes, Oportunidades, Positivo)

* [Foco Criativo e Direcional: Baseado em Visão e Execução]
  └── Chapéu Vermelho (Emoções, Sentimentos, Inexplicável)
  └── Chapéu Verde (Criatividade, Inovação, Soluções)
  └── Chapéu Azul (Visão Global, Implementação, Controle)
```
<pre>
Exemplo: Sistema de Agendamento de Consultas Médicas

[BRANCO] - Dados: Números de Pacientes e consultas por dia 

[VERMELHO] - Emoções: Pacientes Reclamam da demora

[PRETO] - Riscos: Conflito de horários 
 
[AMERELO] - Benefícios: Redução de Filas

[VERDE] - Ideias: Agendamento online ou app

[AZUL] - Organização da discussão

## Arqueologia de Software 

- Analisar sistemas existentes ou legados 

- Investigar código-fonte e artefatos do sistema

- identificar requisitos e regras de negócio

- Usado para documentação incompleta ou ausente.

- Podem ser analisados: Código-fonte, scripts, banco de dados, interfaces, configurações, logs, documentação disponivel

Exemplo: Sistema antigo de Folha de pagamento: Analisar o código para encontrar cálculos salariais, impostos, benefícios. 

## Leitura Baseada em Perpectiva 

Consiste em Analisar documentos de requisitos, partir de diferentes perspectivas para identificar problemas, requisitos ausentes e inconsistências. 

Exemplo de Perspectivas: Usuários, Desenvolvedores, testador, cliente. 

[Visão do Usuário] - Facilidade de uso, funcionalidades, fluxo de tarefas( PERGUNTE: O sistema atende as necessidades do usuário)

[Visão do Desenvolvedor] - viabilidade técnica, arquitetura do sistema, complexidade de implementação. (PERGUNTE: Os requisitos são claros para a implementação)

[Visão do Testador] - Testabilidade, critérios de aceitação, casos de teste possíveis (PERGUNTE: Os requisitos podem ser testados) 

- Desvantagens: Requer tempo, treinamento e boas definições de visões. 

# Passo 4 - Técnicas de Observação

Os analistas de requisitos observam diretamente os usuários, processos, ou sistema em ação

Objetivo: Entender o processo real de trabalho, identificar tarefas realizadas, descobrir problemas existentes, identificar requisitos implícitos. 

- Tipos de Observação: 
    
    - Passiva: Pouca interferência, Coleta de informações Reais
    - Ativa: Interage diretamente com o usuário, faz perguntas, participa de atividades, esclarece dúvidas, durante o processo. 
    
- Etapas de Obsevação: 
    1 - Planejar a obsevação
    2 - Identificar usuários e atividades
    3 - Acompanhar o trabalho no ambiente real
    4 - Registrar informações observadas
    5 - Analisar e documentar requisitos
    

- Vantagens: Processos reais, visualizar atividades não documentadas, revela problemas reais, melhor compreensão do contexto de trabalho. 

- Desvantagens: Demorado, usuários mudam de comportamento ao serem observados, exige acesso ao ambiente de trabalho, pode gerar informações demais

# Slide 3 - Modelagem

- Conceitos Fundamentais 
- Tipos de Modelagem
- Introdução á UML
- Diagramas de Caso de uso

Modelagem de Software: Processo de representar um sistema utilizando modelos abstratos. 

Objetivos: Visualizar o sistema antes da implementação, documentar a estrutura e comportamento, reduzir complexidade, facilitar comunicação entre equipe. 

Porque Modelar: Melhor entendimento do sistema, identificar problemas antes da implementação, comunicação entre desenvolvedores, documentação do projeto, facilita a evolução do projeto. 

O que é um Modelo: Uma representação simplificada da realidade. Exemplos: Planta de uma casa, mapa de uma cidade, diagrama de um sistema. 

Modelos representam: 
    - Estruturas do Sistema
    - Comportamento 
    - Interação entre componentes 
    
## Especificação de requisitos 

### Recursos para modelagem 
    
- Recursos de Negócios 
- Processos de Negócios 
- Regras de Negócios
    
#### Recurso do Negócio

- Recursos humanos: Funcionários, Gerentes, clientes, fornecedores, 

- Recursos Materiais: Equipamentos, máquinas, produtos

- Recursos Informacionais: Dados, documentos do sistema

- Exemplo: Biblioteca 
    - Obra 
        - Livros
        - Revistas
    - Ficha Catalográfica 
        - Título
        - Autor
        - Cidade
        - Ano de Publicação
        
#### Processos do Negócio
    
- Atividades em que o estado do negócio é altear ado

- Um processo descreve como uma atividade é realizada no negócios

- Conjunto ordenado de atividades contendo: Começo e fim bem definidos, entrada e saídas especificadas. 

- Exemplo: Biblioteca
    - Emprestar livro
    - Devolver Livro
    - Reservar obra
    - Pesquisar obra
    - Entre outros 
    
#### Regras de Negócio 

- Condições que definem ou restringem algum aspecto do negócio

- Representam um conhecimento a respeito do negócio

- Definem como os processos devem ser executados

- Exemplo: Emprestar livro da biblioteca

    - O empréstimo de obras da biblioteca pode ocorrer apenas para usuários previamente cadastrados
    - Devolução atrasada tem multa de 1,50 por dia.

#### Diagramas de Caso de Uso

- Representação Gráfica que descreve as funcionalidades propostas para o sistema que está sendo projetado.

- Muito usado para levantamento de requisitos funcionais do sistema

- Um caso de uso representa uma unidade discreta de interação entre um ator (Humano, dispositivo, ou outro software) e o sistema. 

- Caso de uso de Negócios: Descreve como é usado por clientes e parceiros [Visão do cliente]

- Caso de uso de Sistema: Representar os requisitos funcionais dos sistemas [Visão do desenvolvedor]

- Atores: Especifica o papel executado por usuário, um dispositivo, outro sistema, que interage com o assunto(sistema)
- Atores: Devem ser EXTERNOS ao sistema
- Atores são representados por bonecos de palito(stick man) 
<pre>
```  
     ○
  /│\
   │
  / \

 
```
<pre>
- Atores podem ser de Negócios ou de sistema, representados sempre pelo boneco
- Ator de Negócio: Colaboradores da empresa
- Ator de sistemas: Usuários do sistema que será desenvolvido

- Casos de uso: Especificação de um conjunto de ações executadas por um sistema, que contem um resultado observável 
- Casos de uso: Representados por uma elipse, como o nome do caso de uso dentro: 

<pre>
```  
  ╭──────────────────╮
 ╱                                   ╲     O nome do caso de uso de ser um VERBO + SUBSTANTIVO
│   Realizar Compra   │    (Indicando a ação ) 
 ╲                                   ╱     Exemplo: Efetuar Login, Cadastrar Cliente  
  ╰──────────────────╯

```
<pre>
- Caso de uso de negócios: Servir Jantar em um restaurante

- Caso de uso de Sistema: Efetuar login no sistema

- Relacionamentos: Define as relações entre elementos do diagrama

- Ajudam a descrever os casos de uso 

- Tipos de Relacionamento: 
    - Associação
    - Agregação 
    - Composição
    - Herança
    - Dependência 

- Associação: Representa um relacionamento estrutural entre duas classes, objetos de uma classe se relacionam a outra classe. 
- Associação: É o relacionamento mais comum em diagramas de classes 
- Associação entre atores e casos de uso: Demonstra que o ator utiliza um caso de uso, requisitando uma função ou recebendo seu resultado. 
- Associação: Representada por uma seta podendo ser direcionada ou não. Exemplo:  Cliente ───────────────────▶ ( Realizar Compra )
- Exemplo de associação entre ator e caso de uso:

<pre>
```  

                                                                        ╭──────────────────────╮             
   ○                                                               ╱                                            ╲
 ─┼─                                  │                           │
  │      ──────────────────────────── │     Agendar consulta      │
  ╱ ╲                                   │                          │
                                                                       ╲                                          ╱
Paciente                                 ╰──────────────────────╯


```
<pre>
- Exemplo de associação com Multiplicidade: A multiplicidade indica quantos objetos podem participar da relação: 

<pre>

```  
                                                                           ╭────────────────────────╮
     ○                                                                ╱                                               ╲
  ─┼─                                   │                             │
   │   ─────────────────────────────────│    Lecionar disciplinas     │
    ╱ ╲                                    │                            │
                                                                           ╲                                             ╱
 Professor    1                 *          ╰────────────────────────╯
 
 Um professor leciona muitas disciplinas --> * 
 Enquanto uma disciplina só é lecionada por um professor --> 1 
 
 - Exemplos de Multiplicidade:
    - 1          | exatamente 1
    - 0..1       |  0 ou 1
    - *          | Muitos
    - 1 .. *     | 1 ou mais 
    

```
<pre>  
- Agregação: Representa uma relação em que os objetos podem existir mesmo sem o todo
<pre>

```  

                                                                           ╭────────────────────────╮

  ─┼─                                    │                            │    Mas professores podem existir independente do Departamento
   │  ◇─────────────────────────────────│   Gerenciar professores    │  
   ╱ ╲                                    │                            │
                                                                          ╲                                             ╱
 Departamento                              ╰────────────────────────╯
 
 - Composição: Também representa uma relação todo-parte, porém mais forte que a agregação. Na composição 
 a parte não pode existir sem o todo. 
 
                                           ╭────────────────────╮
     ○                                                                 ╱                                       ╲
  ─┼─                                   │                        │   Um pedido possui itens 
   │  ◆─────────────────────────────────│    Visualizar itens    │   Itens não podem existir sem Pedidos
   ╱ ╲                                    │                        │
                                         ╲                                        ╱
  Pedido                                   ╰────────────────────╯
  
 
```

 - Dependência: <<include>> : O relacionamento com include indica que um caso de uso sempre inclui outro caso de uso como parte do seu comportamento. 
    - Um caso de uso reutiliza obrigatoriamente outro caso de uso 
    - O caso incluído é executado sempre que o caso principal ocorre

```  
- Dependência: <<Extend>> indica que um caso de uso pode estender o comportamento de outro em determinadas condições. 
    - A execução ocorre apenas em situações específicas 
    - Diferente do include, o extend não é obrigatório 
    
     ○
  ─┼─                       ╭──────────────────────╮
   │  ──────────────────────│    Realizar saque    │
   ╱ ╲                                         ╰───────────△──────────╯
                                                                       ┊
 Cliente                                ┊
                                                                       ┊  <<extend>> 
                                                                       ┊
                                                  ╭───────────┴──────────╮
                             │ Imprimir comprovante │
                                                   ╰──────────────────────╯
                             

```

- Diferença entre Include e Extend

<pre>
```  
┌───────────────────┬─────────────────────────────┬─────────────────────────────────┐
│ Característica    │ <<include>>                 │ <<extend>>                      │
├───────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ Execução          │ Sempre ocorre               │ Ocorre apenas em certas         │
│                   │                             │ condições                       │
├───────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ Tipo              │ Obrigatório                 │ Opcional                        │
├───────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ Objetivo          │ Reutilização de             │ Extensão de comportamento       │
│                   │ funcionalidade              │                                 │
├───────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ Direção da seta   │ para o caso incluído        │ para o caso base                │
└───────────────────┴─────────────────────────────┴─────────────────────────────────┘

```
